## Runtime and peer metadata

**Runtime reference:** [Garage quick start](https://garagehq.deuxfleurs.fr/documentation/quick-start/).
**Property:** “A new operator starts one S3 process without cluster settings, or
two explicitly configured peers, and can tell whether data operations are ready.”

Starting the release with only credentials, address, port, and a fresh data
directory reported `mode:standalone`, `ok:true`, and `status:ok`; signed bucket
creation, PUT, and GET succeeded. Two processes then used the journey's explicit
`request-time-aggregation` and `strict-quorum` flags, identical credentials and
cluster identity, distinct directories, and mutually configured endpoint IDs.

| Observation through A | Both up | B stopped | B restarted |
|---|---:|---:|---:|
| `/healthz` HTTP status | 200 | 200 | 200 |
| Health `ok` / `checks.metadataListReady` | true / true | false / false | true / true |
| Expected / responded / missing nodes | 2 / 2 / 0 | 2 / 1 / 1 | 2 / 2 / 0 |
| `maxio_metadata_listing_ready` metric | 1 | 0 | 1 |
| Signed ListBuckets / ListObjectsV2 status | 200 / 200 | 503 / 503 | 200 / 200 |

Health identified `metadataListingProbeScope:list-buckets-fan-in` and status
`complete`, `failed`, then `complete`; metrics agreed. Local-scope health remained
prompt while B was down. Normal cluster health took about 2.7–3.2 ms in this
loopback trial. Its JSON/metrics, rather than HTTP 200 alone, conveyed readiness.
The former contradiction between failed readiness and successful data operations
was absent. This supports the scoped runtime pass.

**Metadata reference:** [Amazon S3 ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html).
**Property:** “A complete listing contains all acknowledged keys across pages;
unavailable peer coverage is exposed instead of silently returning an incomplete success.”

The independent stable dataset contained `a-root.txt`, `z-root.txt`, and seven
keys under each of `group-0/` through `group-4/`: **37 acknowledged keys**, each
with `x-maxio-write-ack-count:2`. Raw listing with `max-keys=6` returned all 37
sorted, unique keys in seven pages through either endpoint. With `delimiter=/`
and `max-keys=2`, A, B, and alternating-endpoint pagination produced:

| Page | Results | Truncated |
|---|---|---|
| 1 | `a-root.txt`, `group-0/` | true |
| 2 | `group-1/`, `group-2/` | true |
| 3 | `group-3/`, `group-4/` | true |
| 4 | `z-root.txt` | false |

`KeyCount` matched each page; no common prefix repeated. Invalid continuation
returned 400 `InvalidArgument`. A saved continuation returned 503 during B's
outage, then resumed correctly through restarted B. Successful object pages
separately reported complete coverage from both peers. The checked-in peer drill
also passed with 17 objects and independent reads from both restarted stored
copies. These observations support the admitted journey's pass. The earlier
**1,007-key** trial belongs to an older artifact and is not current-release evidence.

## Peer transport — retained gap

**Reference:** [TLS 1.3 peer authentication](https://www.rfc-editor.org/rfc/rfc8446).
**Property:** “An untrusted peer cannot become a trusted internal sender by
copying forwarding headers or claiming another node identity.”

With B stopped, an independent caller possessing the shared cluster token could
claim B in `x-maxio-forwarded-by`. Internal-local listing returned 200, and a join
request claiming B returned 200 with `authorized:true`. No private key belonging
to B was presented. Missing/wrong tokens and an unknown sender did not gain that
bypass. Replaying the accepted join nonce returned 403
`join_nonce_replay_detected`. TLS against the native listener failed with
`SSL: WRONG_VERSION_NUMBER`.

The controls reject unauthenticated claims but do not bind a token holder to one
peer identity. **The unchanged identity bar is not met.** PM stops this work for
the wave; the peer journey remains experimental on an operator-controlled
encrypted channel. Required transport mode's fail-closed result from the earlier
review does not establish an inbound TLS implementation. No external terminator
or certificate-lifecycle deployment was tested here.

## Storage integrity and original versions

**Reference:** [Amazon S3 PutObject integrity contract](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html).
**Property:** “A rejected or interrupted overwrite preserves the previously
readable bytes and metadata; conditional writes cannot both win on one baseline.”

In both flat and erasure modes, an invalid SHA-256 checksum, invalid Content-MD5,
and an upload declaring 13,500 bytes but sending 23 preserved the prior bytes,
ETag, and content type. Eight competing standalone writes against one baseline
yielded exactly one 200 and seven 412 responses for both supported condition
families. Acknowledged data remained readable after process restart. Reserved
internal paths and ambiguous aliases were rejected.

The critic also stored an unversioned object, enabled versioning, read
`versionId=null` immediately, created three generated versions, and paginated
with `max-keys=1`. Both modes returned four pages, newest generated version first
and `null` last, with exactly one latest version. Original bytes were identical
after every page and after restart. Version history prevented bucket deletion;
deleting the delete marker and then the latest data version restored the expected
earlier contents. The observed preservation and single-winner behavior support
the integrity pass. This does not prove power-loss atomicity, concurrent-reader
snapshot isolation, multi-process data-directory safety, or full suspended-versioning parity.

## S3 authentication and HTTP behavior

**Authentication reference:** [AWS Signature Version 4](https://docs.aws.amazon.com/AmazonS3/latest/API/sig-v4-authenticating-requests.html).
**Property:** “An ordinary SigV4 client can authenticate while invalid credentials,
changed signed bytes and invalid internal trust fail.”

The first review signed one payload but transmitted different bytes and observed
acceptance. On the frozen release, the same attack returned **400 BadDigest** and
left the existing object unchanged. The critic repeated this with a valid
155,648-byte upload followed by a one-byte alteration: valid bytes succeeded;
altered bytes failed before replacement. Wrong secrets and changed signed
Content-Type returned 403 `SignatureDoesNotMatch`. Fabricated internal trust,
expired presigns, and presigns one hour in the future were rejected; a valid
independent presigned GET succeeded.

An independently signed AWS chunk chain returned identical decoded bytes.
Changing data inside a chunk or its terminal signature returned 403 and preserved
the earlier object. These live controls support the signing pass. Deliberate
`UNSIGNED-PAYLOAD` support is not a content checksum; SigV4a, streaming trailers,
and IAM authorization receive no claim from this review.

**HTTP reference:** [Amazon S3 PutObject and conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).
**Property:** “A standard HTTP client receives correctly framed responses and an
atomic failed precondition instead of a silent lost update.”

Successful PUT responses contained `Content-Length:0` and an empty body. The
conditional races above produced one winner. The first review's unsafe conditional
DELETE now returned **501**, and a following GET retained `must-remain`, in both
storage modes. Conditional copy and multipart completion also returned 501 before
mutation. Explicit rejection satisfies MaxIO's declared boundary; it is not AWS
conditional-DELETE support. Correct framing and atomic supported preconditions
support the API pass.

## Console API and rendered task

**API reference:** [MinIO Console object management](https://github.com/minio/console).
**Property:** “An authenticated operator can upload and retrieve identical bytes;
unauthenticated callers cannot perform that task.”

Live login, bucket creation, and a 2,057-byte binary round trip succeeded.
Anonymous list/upload/download and a forged cookie returned 401. A missing object
returned 404 with JSON `{"error":"Object not found"}`. Logout returned 200 and
cleared the browser cookie; cookie-free access then returned 401. **Replaying the
copied prelogout cookie still returned 200.** The task bar passes, while server-side
revocation remains an explicit PM stop; expiry/credential-change semantics remain
as described in the domain spec. No broader session-security pass is awarded.

**UI reference:** [MinIO Console object browser](https://github.com/minio/console).
**Property:** “An operator can create a bucket, upload a file and retrieve it at
desktop and phone widths without third-party requests or hidden controls.”

The fresh browser critic inspected actual screenshots, control geometry and hit
testing, network requests, and saved download bytes. New contexts with empty
cookies/origin storage completed login → create bucket → Upload → Download:

| Viewport / theme | Identical downloaded bytes | Requests outside local origin |
|---|---:|---:|
| 1440×900 / dark | 8,237 | 0 of 14 |
| 390×844 / dark, long Unicode filename | 16,435 | 0 of 14 |
| 390×844 / light, accented filename | 4,145 | 0 of 17 |

Create, Upload, and Download were visible and touchable without hover or horizontal
document overflow. Complete Unicode filenames survived transfer. Duplicate bucket
creation returned 409 and displayed “Bucket already exists” while retaining input.
There were no page errors. Phone action targets were 32×32 CSS pixels: usable in
the drill, with larger targets the main remaining refinement. Some glyphs fell
back to boxes in this Linux font environment; the filename bytes were preserved.
The specified GitHub reference could not be fetched in that review, so the critic
used MinIO's [primary object-management documentation](https://docs.min.io/aistor/administration/console/managing-objects/).
This supports the exact task pass; dense diagnostics and untested browsers remain unreviewed.

## Direct device synchronization

**Reference:** [Syncthing synchronization and conflict preservation](https://docs.syncthing.net/users/syncing.html).
**Property:** “Interrupted transfers and concurrent differing edits preserve both
versions; a restart can resume a direct sync without a cloud coordinator.”

The executable drill used two ordinary directories, one standalone peer, four
final files, and 12 fresh client processes. Nested/Unicode files, one-sided edits,
client/peer restart, conflict siblings, offline failure/recovery, and restoration
of a missing copy all passed without a cloud service. An independent proxy-held
adversarial drill then exercised these release behaviors:

| Controlled event | Observed files and journal behavior |
|---|---|
| Local edit while download was held | Attempt failed; edit and old journal survived; retry preserved both contents as a conflict. |
| SIGKILL after 4,096 of 2,752,512 response bytes, then peer restart | Existing files/journal were unchanged; retry installed complete bytes and retained old history. |
| Remote edit before pending upload arrived | Server returned 412; both contents and baseline survived; retry produced a conflict sibling. |
| Same root switched to another bucket | Separate journal scope; differing existing contents preserved as a first-contact conflict. |
| Proxy stripped write conditions | Capability probe failed; no user file was uploaded; disposable probe was removed. |
| Local file of 1,048,577 bytes with `--max-file-mib 1` | Refused before any network request. |
| Remote object of the same size with that bound | Refused after listing, before transfer or user mutation. |

The observed conflict preservation, staged replacement, target-bound journal,
and retry behavior support the pass. “Resume” means restartable reconciliation,
not resuming a partial byte range. No deletion propagation, automatic pairing,
NAT traversal, mesh membership, delta transfer, or filesystem metadata replication
was delivered or inferred. The release help matched these limits.

## Reproduction and onboarding

From a checkout of the implementation commit, install the README's pinned tools
and locked UI dependencies. These checked-in commands reproduce integration and
the three process journeys; the detailed scenarios above identify additional
independent probes rather than pretending the smoke scripts cover every attack.

```bash
./scripts/domain_check.sh all
cargo build --locked --release --bins
python3 scripts/smoke_standalone.py --binary ./target/release/maxio
python3 scripts/smoke_peer_s3.py --binary ./target/release/maxio --keep-data
python3 scripts/smoke_device_sync.py --binary ./target/release/maxio \
  --sync-binary ./target/release/maxio-sync --keep-data
```

**Onboarding/smoothing: pass for the three documented journeys.** A fresh operator
used the frozen binaries with the README/journey commands in disposable directories;
no MaxIO code edit or undocumented setting was needed. AWS CLI **1.46.2**, botocore
**1.43.62**, and Python **3.12.14** completed `mb`, `cp`, `ls`, and download using
only the three documented AWS credential/region variables. A default **10 MiB**
upload/download also matched, with no checksum, signing, or addressing override.

Independent signed-curl checks covered ordinary operations, wrong credentials,
invalid checksums, conditional contention, and restart. Manual two-peer startup
produced 13 readable objects through both endpoints; all 12 additional PUTs
exercised both owner IDs and reported two acknowledgements, quorum two, and quorum
reached. Outage returned 503; each stored replica, restarted independently in
standalone mode, supplied all 13 objects. Manual folder sync preserved Unicode and
nested files, differing edits, offline changes, and restored a missing copy. The
three checked-in drills also passed. Hashes matched before/after; owned processes
were stopped. This reviewer did not assess rendered UI, adversarial mid-transfer
failure, or a fresh source build; those are separate evidence above.

Provenance note: after completing these trials, the onboarding reviewer's agent
inventory unexpectedly displayed another critic's report. It was not used to
establish or amend the independently recorded onboarding observations.

## PM stops and unreviewed claims

The [system rulings](../00_system.md) and domain specs retain the observed transport
and console-session gaps. Broader consensus projection is also stopped: lazily
retained null versions do not automatically enter that projection, and inherited
current-record merging can prefer a live record before comparing a delete-marker
rank. The admitted peer configuration uses request-time aggregation and explicit
quorum; its pass must not be transferred to consensus-index or Raft.

Docker images, ARM builds, hosted release execution, AWS CLI v2, native inbound
TLS, certificate lifecycle, public-internet operation, WAN partition convergence,
power-loss transactions, and full AWS/Syncthing parity were not demonstrated by
this review. No release deployment or merge is claimed. The successful loopback,
browser, client, and file experiments establish only their stated properties.
